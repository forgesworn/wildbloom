What it is

One tool for your files. One home for their encrypted bytes.

The browser prepares and encrypts a file, asks your Nostr signer to approve exact actions, and publishes a signed pointer. Wildbloom Node stores the bytes on a machine you control and exposes a standard Blossom service through your HTTPS setup or a stable Tor onion address.

Why it exists

A URL is not custody.

Servers disappear

A Blossom URL proves where bytes were once available. It does not promise that somebody else will keep paying for the disk.

Home hosting is awkward

Router rules, changing IP addresses and carrier NAT make a simple home server needlessly hostile. Optional Tor removes that inbound networking chore; people with HTTPS infrastructure can use it directly.

Redundancy must be visible

Choose complete encrypted copies or recoverable shards. Wildbloom reads bytes back and verifies their hashes before counting them as stored. Choose nodes with independent failure risks.

How it relates to Blossom

Blossom does the storing. Wildbloom handles everything around it.

Blossom is the storage protocol: put bytes on a server, fetch them back by their SHA-256. Wildbloom uses it unchanged and talks to any Blossom server, not only its own. What it adds happens before the upload and after the server is gone.

None of this is exclusive. Other Blossom clients encrypt, other servers mirror, and Wildbloom files are ordinary blobs any Blossom server can hold. Wildbloom brings these choices together in one explicit workflow and tells you where each guarantee stops.

When you do not need Wildbloom

Posting a public picture in a note? A hosted Blossom server is simpler, and encryption only gets in the way. Wildbloom earns its keep when the host should not read the file, or when the file has to outlast the host.

Replication & sharding · preview

A failed disk should not take your only copy.

A home node can go offline. A host can close. Replication and sharding let you spread encrypted storage across nodes you choose, so losing one does not have to mean losing the file. Choose how much storage to use, how much loss to tolerate, and whether each node receives a complete encrypted copy or just a part.

ONE NODE

Keep it simple

Use one node when you already keep a separate backup, or can upload the file again. It uses the least storage, but that node going offline makes its copy unavailable.

REPLICATION

Keep complete copies

Put two or three complete encrypted copies on separate nodes. Any one verified copy can restore the file. Choose this for straightforward recovery; two copies use twice the storage, three use three times.

SHARDING + ERASURE CODING

Share the storage

Split the encrypted file into parts, with extra parts for recovery. Choose this to spread storage across trusted nodes and send each only its assigned part. You need a threshold of different parts to restore the file.

Spread the risk as well as the bytes

Two nodes on the same disk, power supply or internet connection can fail together. Use independent machines and locations, and group nodes that share a failure risk. Wildbloom reads bytes back and verifies their hashes before counting a copy or part as stored.

Repair before another node is lost

After a loss, the remaining copies or parts leave less room for another failure. Restore redundancy in the browser, or import the signed receipt into Wildbloom Node and explicitly enable owner repair while the browser is closed. Repair needs enough surviving parts, an external signer and available storage at approved destinations. It works on encrypted bytes without your recovery key.

Want each storage node to hold only a part? Choose sharding. Upload and repair send each node only its assigned part; reconstruction happens in your browser or on your separate owner repair machine. Encryption protects the contents. Splitting alone does not stop operators combining parts, or fetching other parts if they obtain your receipt.

Keep your route back to the file. Save the private signed receipt, which records where the parts belong, and back up the recovery key separately. Extra parts cannot replace either one. Keep an independent backup of irreplaceable files too.

You choose the pool. Nodes keep their own quotas and retention rules. Replacement destinations need a new signed receipt. Find recommendations from trusted signed server lists, then choose which nodes to contact. Free-capacity discovery, draining and cluster-wide rebalancing are not available.

Protocol

Open protocols. A clear route back.

  1. 1
    Prepare

    The browser encrypts content, filename and MIME type locally, then calculates the payload's SHA-256.

  2. 2
    Authorise

    Your signer approves a short-lived BUD-11 action for one hash and one Blossom host. Wildbloom never asks for an nsec.

  3. 3
    Store and replicate

    BUD-02 uploads the exact bytes. BUD-04 lets another authorised node mirror them, and each node verifies the content hash.

  4. 4
    Keep the recovery record

    Single-file publishing uses a signed NIP-94 event. Pools use a private signed receipt saved to your device, without relay publication or torrent discovery.

  5. 5
    Verify

    Retrieval is not complete until the byte count and SHA-256 match the signed event. Decryption happens locally.

Storage you direct. Wildbloom is interoperable storage and owner-directed replication and shard repair. Nodes do not discover strangers, promise permanent custody or create replicas without somebody explicitly asking them to. An explicitly configured owner service can keep repairing while your browser is closed. Two nodes mean two copies only after mirroring succeeds and both hashes verify.

Privacy, in practice

Your content is private. Connections still leave clues.

Encryption protects file content, not timing, byte counts or a reused public identity. Nostr relays provide discovery, not the file bytes. Tor is optional and hides the node's home address, not every behavioural clue. Direct mode exposes ordinary network metadata. The experimental direct browser swarm remains an optional compatibility path and can expose IP addresses; the Wildbloom Node path does not use WebRTC, STUN or TURN.

Choose your infrastructure

Network profile

Use Tor Browser rather than SOCKS-proxying a normal browser. Wildbloom cannot prove that this browser is using Tor; an ordinary browser lacks Tor Browser's fingerprint protections and may not provide Web Crypto on HTTP onion origins. Tor-only mode refuses clearnet endpoints and disables WebRTC, but a NIP-07 add-on or reused Nostr key can still fingerprint or identify you.

One node holds the encrypted file. Keep a separate backup: this layout has no redundancy.

Pool files are always encrypted. Split mode sends each node only one coded part; reconstruction and repair happen in your browser or an explicitly configured owner repair service. Operators may collude or fetch other parts if they learn their addresses. Encryption protects the contents. Keep the signed pool receipt privately alongside a separate recovery key; pool receipts are not published to relays or swarms.

Inspect the file to validate placement. Extra failure groups provide spare destinations. A signed receipt describes intended placement; only verified reads count as stored parts. Keep the receipt even if an upload is interrupted.

Peer mode has no hidden public STUN or TURN default. That avoids an undeclared third party, but peer connections may fail across networks until an operator-controlled ICE policy is reviewed and configured.

Find nodes, buy storage and verify storage

Each action is separate. Discovery is a recommendation, payment buys an allowance, and a storage check verifies current retrievability.

Discover recommended nodes

Results come from signed Blossom server lists published within 30 days. A recommendation does not prove ownership, capacity or independent failure domains. Nodes are contacted only after you choose an action.

Buy storage directly from this node

Uses the Blossom server selected above. Lightning and LNURLcash are paid directly to its operator. Checkout is currently available in direct mode only; external wallets have their own network behaviour.

After a timeout or cancellation, check the same order. Do not pay a second time. An activated allowance is not proof that a file was uploaded or replicated.

Verify storage with a fresh challenge

First resolve a signed file event or private pool receipt below. This reads every selected encrypted byte and independently downloads it for verification. It needs no decryption key. Large checks use bandwidth. Passing proves current retrievability, not continuous retention or a dedicated physical copy.

Retrieve and verify

Look up a signed event on your relays or verify a saved event locally, then choose how to fetch the file.

If the original server is unavailable, enter a server that already holds a copy before resolving the event. Leave blank to use the signed event's URL. A Blossom fetch contacts only the chosen server, which sees your connection and the file's hash. The signed size, hash and encryption checks still apply. This does not create a replica or prove ongoing storage.

Use a saved signed event without a relay

Load the signed file event you saved or received, or paste its JSON below. Verification checks its signature and file information locally. Check the author or retained event ID before fetching; a valid signature alone does not identify someone you trust.

Repair reconstructs ciphertext locally without a recovery key, then uploads only the intended parts to their approved nodes. Connect the receipt author’s signer first. The browser must remain open.
