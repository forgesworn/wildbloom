Is Wildbloom ready for my only copy?

Keep another backup. Encrypted storage, recovery and repair have automated acceptance coverage, and live one-Mac LNURLcash purchase, recovery and paired backup restore have passed. Independent security review, broader physical-device testing, hosted-operator and refund acceptance remain open.

Read the acceptance evidence ↗
Can a storage node read my file?

With encryption enabled, nodes receive encrypted content, filename and file type. Your separate recovery key unlocks the file. Connections still reveal metadata such as timing, byte counts and, in direct mode, IP addresses. Optional Tor reduces address exposure; it does not remove every clue.

Understand the privacy boundary ↗
Can I keep the whole file off every node?

Choose erasure-coded sharding. Upload and repair send each storage node only its assigned part. Reconstruction happens in your browser or separate owner repair service. Encryption protects the contents; splitting alone does not prevent operators combining parts or fetching other parts if they obtain your receipt.

Does repair happen automatically?

You can explicitly enable a separate owner repair service in Wildbloom Node. It works on encrypted bytes without the recovery key, but needs enough surviving parts, an external signer and approved storage destinations. Repair authority expires and needs approval again after restarting the app. Free-capacity discovery, draining and cluster-wide rebalancing are not available.

Set up owner repair ↗
What do I need to recover a file?

Your signed file event or private pool receipt, the separate recovery key, and enough available verified bytes or parts. Save the record and key before closing the browser. Extra copies cannot replace a lost recovery key. Ordinary file recovery needs no signer.

01

Choose your infrastructure

No endorsed defaults. You decide which services learn about the file.

Network profile

Use Tor Browser rather than SOCKS-proxying a normal browser. Wildbloom cannot prove that this browser is using Tor; an ordinary browser lacks Tor Browser's fingerprint protections and may not provide Web Crypto on HTTP onion origins. Tor-only mode refuses clearnet endpoints and disables WebRTC, but a NIP-07 add-on or reused Nostr key can still fingerprint or identify you.

One node holds the encrypted file. Keep a separate backup: this layout has no redundancy.

Pool files are always encrypted. Split mode sends each node only one coded part; reconstruction and repair happen in your browser or an explicitly configured owner repair service. Operators may collude or fetch other parts if they learn their addresses. Encryption protects the contents. Keep the signed pool receipt privately alongside a separate recovery key; pool receipts are not published to relays or swarms.

Inspect the file to validate placement. Extra failure groups provide spare destinations. A signed receipt describes intended placement; only verified reads count as stored parts. Keep the receipt even if an upload is interrupted.

Peer mode has no hidden public STUN or TURN default. That avoids an undeclared third party, but peer connections may fail across networks until an operator-controlled ICE policy is reviewed and configured.

+

Find nodes, buy storage and verify storage

Each action is separate. Discovery is a recommendation, payment buys an allowance, and a storage check verifies current retrievability.

Discover recommended nodes

Results come from signed Blossom server lists published within 30 days. A recommendation does not prove ownership, capacity or independent failure domains. Nodes are contacted only after you choose an action.

Buy storage directly from this node

Uses the Blossom server selected above. Lightning and LNURLcash are paid directly to its operator. Checkout is currently available in direct mode only; external wallets have their own network behaviour.

After a timeout or cancellation, check the same order. Do not pay a second time. An activated allowance is not proof that a file was uploaded or replicated.

Verify storage with a fresh challenge

First resolve a signed file event or private pool receipt below. This reads every selected encrypted byte and independently downloads it for verification. It needs no decryption key. Large checks use bandwidth. Passing proves current retrievability, not continuous retention or a dedicated physical copy.

02

Publish a file

Inspect your file, save its recovery key, then approve the upload. Keep the signed file event or pool receipt for recovery.

External signing handoff

The handoff exposes the intended service and metadata, and the returned event adds the public signing identity. Transfer it deliberately. Never paste a private key or recovery key here.

Optional: configure trackers before uploading to make this file available to peers.

Signing creates a NIP-94 file event locally. Configured trackers also add a NIP-35 torrent index.

Save the signed file event to recover without a discovery relay. It contains public metadata, never the file or its recovery key. Keep the recovery key separately.

03

Retrieve and verify

Start with your saved file event or pool receipt. Verify it locally, enter the recovery key when asked, then fetch and save the verified file. No signer is needed for ordinary recovery.

If the original server is unavailable, enter a server that already holds a copy before resolving the event. Leave blank to use the signed event's URL. A Blossom fetch contacts only the chosen server, which sees your connection and the file's hash. The signed size, hash and encryption checks still apply. This does not create a replica or prove ongoing storage.

Use a saved file event or pool receipt

Load the signed file event or pool receipt you saved, or paste its JSON below. You do not need to configure relays or a publishing layout for this. Verification checks its signature and file information locally. Check the author or retained event ID before fetching; a valid signature alone does not identify someone you trust.

Repair reconstructs ciphertext locally without a recovery key, then uploads only the intended parts to their approved nodes. Connect the receipt author’s signer first. The browser must remain open.
